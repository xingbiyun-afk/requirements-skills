# 横向规则（多页面 / 多端共用）写作规格

当一个业务规则不只服务一个页面，而是被多个入口、多个端或多个文档共同消费时，按本规格处理。目标是：**规则只在一个权威位置完整成文，各消费方按自己的职责写清来源、使用方式、影响和差异，不重复、不遗漏、不互相矛盾。**

普通单页规则不需要套用本规格；先判断影响面，再决定深度。

## 1. 何时按横向规则处理

满足任一条件即可考虑：

- 同一规则影响 ≥2 个**消费侧重不同**的页面/入口/端（例如配置/维护页与发起/交易页，而不是同一列表与详情只是展示同一字段）；
- 同一规则影响多个端或多个仓（例如 Web 与 App，或管理端与执行端）；
- 同一规则有多个消费动作（展示、选择、提交、审批、审计、导出）；
- 规则存在状态、时点、例外或终态，且不同消费方对同一字段的读写时机不同；
- 用户或评审反馈“规则散落、同一件事多处说法、压成一句话看不懂”。

不满足以上条件时，按普通页面规则写，不额外要求全量盘点或横向矩阵。

## 2. 规则包：唯一权威 + 消费方

先定义一个“规则包”，而不是直接往某个页面文档里补一句。

| 组成 | 要写什么 |
|---|---|
| 规则身份 | 规则名、业务对象、回答的业务问题；避免一个名称混指多个概念 |
| 唯一权威落点 | 规则值在哪个 PRD、页面规则明细或契约中完整成文；其他文档只能摘要 + 回链 |
| 字段与字典 | 相关字段、状态、枚举、展示文案的完整字典（按 `page-rule-spec.md` 字典规则） |
| 判定结构 | 触发条件 → 结果；多条件按判定顺序列出，不压成一句 |
| 例外与时点 | 例外场景、时间边界、终态、可逆性、读取时点、快照或实时 |
| 消费方矩阵 | 谁消费这条规则、消费什么、在什么时点读、需要写到多细、端/仓差异 |
| 回链与未定 | 各文档回链权威落点；未定事项集中登记，不在下游文档猜填 |

**权威唯一**不等于“所有内容都塞进一个文件”。正确做法是：权威文档完整；下游文档写摘要、来源、消费方式和本页影响；通过回链让读者能到达完整规则。

## 3. 消费方矩阵

（投影到各消费方的侧重、双轨同步触发与横向规则投影见 `projection-and-governance.md` §2.2.1 与 §2.2。）

至少覆盖实际存在的消费方；没有的不要虚构。

| 消费方 | 该方要回答的问题 | 建议写到什么程度 |
|---|---|---|
| 管理/配置页 | 规则值是什么、如何配置、有哪些状态和例外 | **完整**：定义、字段、判定顺序、字典、异常/终态、配置约束 |
| 发起/交易页 | 这个标识/资格从哪里来、何时读取、影响哪一步操作、什么情况不可用 | **来源 + 使用 + 影响 + 例外**：摘要判定顺序，回链权威；不复制完整配置规则 |
| 详情/审计页 | 展示的是当前值还是历史快照、只读边界、异常/终态如何呈现 | **展示时点 + 只读边界 + 快照口径**；不重新定义规则 |
| 另一端/另一仓 | 同业务含义如何消费、读写时点、哪些差异是合理适配、哪些待承接 | **消费方式 + 差异 + 状态**；明确只读参考或待实现，不能以一端完成代替另一端 |
| 导出/报表/消息等 | 使用哪个时点的值、是否受权限或状态影响 | **取值时点 + 过滤/权限 + 失败表现** |

写法要求：

1. 管理/配置页给完整规则；交易页只给来源、影响和例外，避免整段复制。
2. 不同消费方对同一字段的展示名可以不同，但业务含义必须能回链同一个权威定义。
3. 多端/多仓时先定“哪份文档是权威”，再写各端消费差异；不要默认某端是母版。
4. 暂时不实现的一端写“本单不承接 / 待后续单 / 只读参考”，并说明是否影响当前交付判断。

## 4. 判定型规则的结构

涉及“可/不可、允许/不允许、满足/不满足”的规则，优先写成结构化判定，不写成一长句：

1. **前置条件**（例如对象存在、状态在范围内、可见性）；
2. **判定顺序**（条件 A → 结果；条件 B → 结果；命中即停止）；
3. **例外**（哪些场景豁免、豁免哪一步、是否仍需其他条件）；
4. **时点/终态**（何时读取、何时复核、状态是否不可逆）；
5. **失败/缺失表现**（字段缺失、数据异常、权限不足、外部变化）。

写法建议：

- 条件多时用编号或“条件 / 结果 / 例外”表格；
- 一条只表达一个判断，避免“并且/或者/同时/另外”堆叠；
- 状态、时点、例外不能因为“精简”而删掉；
- 同一概念固定一个名称；近义名称必须解释差异，不能互换。

## 5. 可读性与完整性

横向规则容易同时出现两个问题：写得太散，和压得太短。

- **权威段**先给结论和适用范围，再展开判定、字典、例外；
- 下游段先写“本页为什么要看这条规则”，再写来源和影响；
- 一节只承担一个读者任务：配置页回答“怎么配”，交易页回答“能不能用/为什么不能用”；
- 能用表格/编号表达的条件，不用长段落；
- 不把“完整”理解为复制全文：下游摘要 + 回链即可；
- 不把“简洁”理解为删条件：影响结果的条件、例外、时点必须保留。

## 6. 双端/多仓的处理

| 问题 | 要写清 |
|---|---|
| 谁是规则权威 | PRD / 页面规则明细 / 接口契约中的唯一位置 |
| 谁是消费方 | 各端/仓的页面、接口、任务；读取/写入时机 |
| 哪些是共性 | 各端相同的业务含义、条件、结果 |
| 哪些是差异 | 权限、入口、展示形态、实现阶段等合理差异及理由 |
| 哪些待承接 | 未实现端的任务、责任方、依赖、是否阻断当前交付 |
| 证据边界 | 一端的代码/测试/Mock 不能证明另一端已实现或生产可用 |

不要把两端写成两套平行规则；如果两端当前确实不同，先确认哪一个是业务权威、哪一个是适配差异，无法裁定的列为待确认。

## 7. 同类问题全量排查

当用户反馈“同类问题多处”、评审发现一个典型散落/压缩句，或横向规则被改动时，做一次有边界的全量排查：

1. **定分母**：明确排查哪些文档/章节/消费方（例如某模块的全部阅读层文档），不笼统写“全项目”。
2. **定问题类型**：多条件压句、规则分散/重复、缺例外/时点、术语不统一、权威缺失。
3. **定权威源**：用户裁定 > 规则正文/契约/代码事实 > 阅读层表达；不能反向用阅读层改规则。
4. **逐项记录**：文档、章节、问题类型、原文摘要、修订、权威源、双轨同步、未改原因。
5. **验收**：分母覆盖 100%；未改项有理由；规则值零变更（除已确认口径）；链接/结构检查通过。
6. **不强制**：小需求、小变更不做全量；只有横向规则/同类反馈/明确要求时执行。

## 8. 反模式

- 一个多条件判断只留一句概括，读者无法知道先后和例外；
- 管理页和交易页各写一套“完整规则”，后来一处改了另一处没改；
- 下游文档只写“按系统规则”或“见相关文档”，没有来源、时点、影响；
- 双端默认一端是母版，另一端只写“同步”但不说明差异/待承接；
- 把历史字段、兼容值、已废止口径混入现行判定；
- 发现同类问题只改示例句，不做有分母的排查；
- 为了“短”删掉影响结果的条件，或为了“全”把实现细节/历史沿革写进阅读层。

## 9. 交付自检

- [ ] 规则包有唯一权威落点；其他文档是摘要 + 回链，不是平行全文。
- [ ] 消费方矩阵覆盖实际消费方；每个消费方回答了“来源、时点、影响、例外”中与其职责相关的问题。
- [ ] 判定顺序、例外、终态、时点、缺失/失败表现可执行、可验收。
- [ ] 同一概念名称一致；近义名称已解释差异。
- [ ] 双端/多仓的权威、差异、待承接和证据边界已写清。
- [ ] 若做了全量排查：分母、逐项记录、未改原因、规则值零变更、链接/结构检查齐全。
- [ ] 没有为了短而丢条件，也没有为了全而复制全文。
