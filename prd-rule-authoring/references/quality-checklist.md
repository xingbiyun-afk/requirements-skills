# 自审与交付检查清单

## 1. 机械检查（每次必做）

对目标文档目录与权威源目录执行（按项目实际路径替换）：

```bash
# 行数比例（阅读层 / 权威源）
wc -l <阅读层文件> <权威源文件>

# 禁词（实现/历史/编号/英文 UI 术语）；命中即需处理或说明
grep -nE '\.(vue|ts|tsx|mjs|js)|Mock|DTO|接口|代码路径|行号|CR-[0-9]{8}|RT-[A-Z]+-[0-9]+|更新记录|更新日志|历史快照|已废止|已退役|/Users/|hover|checkbox|tooltip' <阅读层文件>

# 标题与文件名一致
head -1 <阅读层文件>   # 应等于文件名去扩展名

# 相对链接可达：本单必查触及文档集；收尾/发布前再全仓机械扫描
# 覆盖：百分号编码文件名、含空格文件名、# 锚点、显式 <a id>
# 输出四项实数：文件数 / 链接数 / 缺失数 / 锚点失效数（只抽查变更文档不算通过）
```

- 禁词命中：技术内容删除；确需保留的边界说明改写为中文业务表述。
- 历史章节：阅读层不得出现「更新记录/更新日志」标题。
- 元写作说明行（“本文不写…”自指句）不进入正文；写作规范放技能与本清单，不放文档。

## 2. 可读性检查（抽读）

按读者路径通读，逐项确认：

| 检查项 | 通过标准 |
|---|---|
| 结构 | 骨架完整、章节顺序符合读者认知、无重复章节 |
| 结论先行 | 每节首句即结论；无“背景铺垫→沿革→例外→实现”式展开 |
| 句长 | 一句一个判断；长句拆开；删除“为了/从而/需要注意的是”等填充 |
| 呈现 | 以要点为主：一件事一条、开头有加粗标签；穷举类用表格；没有多段连续叙述；同一文档内各章节呈现方式一致，新增章节照既有写法 |
| 术语 | 同一概念固定名称；中文化；首次出现的技术标识有业务解释 |
| 完整性 | 每个页面/模块能回答：给谁用、有什么、怎么操作、什么时候不可用、异常怎么办、边界在哪 |
| 未定 | 待确认事项表完整；正文未定处有【待确认】；无“冒充已定” |
| 依据 | 关键规则能在权威正文找到出处；无新增/修改规则值 |

抽读建议 3~5 份或每批 2~3 份，重点看页面级与模块级各一份。

## 2.1 横向规则检查（按适用性）

- [ ] 规则有唯一权威落点；下游页面是摘要 + 回链，不是平行全文。
- [ ] 消费方矩阵覆盖实际页面/入口/端；每个消费方写清来源、时点、影响、例外中与自身职责相关的部分。
- [ ] 判定顺序、例外、终态、时点、缺失/失败表现完整；没有为“短”删条件。
- [ ] 管理/配置页与发起/交易页侧重不同，术语一致，近义名称已解释差异。
- [ ] 双端/多仓已写权威、差异、待承接和证据边界，没有以一端代替另一端。
- [ ] 如做同类全量排查：分母明确、逐项记录、未改项有理由、规则值零变更、链接/结构检查通过。

## 2.2 读者测试（长文档或多章节时启用）

作者按读者路径自检，容易「以为自己看懂了」。本节用一个**不带任何上下文的读者实例**验证文档能否被读懂。

**与定稿复核分工**（两者都要，不可互相替代）：

- **定稿复核**（更强模型）：只找错——不可执行的表述、未闭合的证据链、未验证却当已完成。
- **读者测试**：只验懂——读者能否在文档里找到答案、会不会误解、需不需要猜。

**适用**：约 700 行以上，或跨多个页面/模块的长文档、批量重构的一批文档。单页小改与短文档不启用（§2 抽读已足够），不要为短文档增加一轮。

**做法**：

1. 按目标读者出 **5 个问题**，覆盖不同章节与不同判断维度。示例角度：某状态何时出现、失败后如何恢复、该字段能否编辑、异常时展示什么、谁有权修改、参数为空时如何表现。
2. 派一个**不带本次任何上下文**的子代理，只给文档路径与这 5 个问题，要求逐题回答并注明依据的章节号。
3. 按回答判定：
   - 能在指定章节找到答案 → 通过；
   - 答「文档没说」、答错、或只能靠猜 → **规则缺口**，回填正文或登记进待确认表；
   - 答出正文没有的结论 → **歧义**，改写该处；
   - 需要多处拼凑才答得出 → **缺前提**，补前置条件或入口指引。
4. 修完用同一组问题复测，直到 5 题均可定位到章节且无新歧义；记录问题、判定、修订位置，作为交付证据的一部分。

## 3. 双轨一致性检查

- [ ] 关键枚举/状态/权限/边界抽样对照（记录 3~5 个点与位置）
- [ ] 阅读层没有权威正文之外的规则值
- [ ] 权威正文近期变更均已反映
- [ ] 文档负责人/口径维护人已填
- [ ] 待确认事项与缺口清单状态一致
- [ ] **现行段的事实（条数/类型数/样本规模/读写边界）带 as-of 依据**；历史计数与旧样本只出现在更新记录或历史表，不裸写在现行段
- [ ] **数据来源或读写边界变化时**，技术真源表与代码中的口径注释已同单同步（不是只改规则正文与阅读层）

## 4. 流程检查

- [ ] 样板先定稿（批量时）
- [ ] 用户确认体例与关键口径
- [ ] 分批边界清晰（模块/文档集合）
- [ ] 每批交付说明包含依据状态与未执行项
- [ ] 台账/索引/入口按项目流程更新（若项目要求）

## 5. 交付说明模板

```
文种与落点：<文种>，落在 <路径>；理由：<读者/职责>
修改范围：<新增/修改/删除文件清单>
依据状态：已确认 <来源>；仓内留底 <来源>；待确认 <条数>；技术待核验 <条数>
未决项与阻断：<列表/无>
通读与链接：<结果；断链数；H1 一致性>
验证证据：<文档检查/抽读/未执行项分别列>
```
