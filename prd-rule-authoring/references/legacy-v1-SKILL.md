# 产品需求文档（PRD）与主页面规则写作

把需求写成接手者能定位、理解和验证的现行规则。借用页面盘点、字段与操作矩阵、异常场景和跨端对照的思路检查写作完整性，按本次影响范围取用，不把普通撰写变成全量审查。

## 1. 核对依据，选择正文落点

确认新增、修改或删除的内容，以及涉及的端、角色和业务对象。读取项目协作入口、现行 PRD、页面规则及相关字段/接口契约、索引和测试追溯；核实实现事实时再查看当前代码。

分别记录已确认业务规则、当前代码事实、技术待核验事项、历史记录和未来规划。历史内容不一定失效，应核对是否已被后续决定替代。来源冲突时列说法、时点和影响；明确已被替代的口径不再沿用，无法判断的交责任方裁定。代码、菜单或受控模拟实现（Mock，仅验证约定范围内的行为）不能代替业务决定，也不能证明生产接口、权限或能力。

优先更新现有权威正文，按职责选落点：

- **整体 PRD**：目标、范围、角色、核心对象、共性流程、跨页面规则和责任边界。
- **主页面规则明细**：入口、同级按钮与标签、列表/区块、子页面、弹窗、提示及从操作到结果的行为。
- **字段/接口契约**：对象的数据模型、服务提供方和请求响应定义；PRD 与页面规则引用其权威位置并解释业务含义。

共性规则集中定义，页面细节放对应规则明细，不复制正文。只有独立职责、生命周期或明显体量才考虑拆文档。调整索引、覆盖矩阵或追溯表前，检查脚本、链接和验收是否使用；它们可以独立保留，但不另立规则正文。

## 2. 按影响范围检查完整性

先找功能路径：从哪里进入、有哪些同级入口、下级页面或浮层、执行什么操作、得到什么结果。核对关联流程与共性规则；删除还追踪旧链接、兼容入口、历史记录、接口消费者和测试。既找需求中尚未写入规则的内容，也找页面已有但规则未解释的行为。新功能尚无代码时，以已确认需求和设计为依据，标明规划状态。

简单修改直接写正文；字段或条件较多时，用矩阵辅助核对，复用已有清单并引用规则位置。矩阵可只用于写作检查，无需新增交付物。普通撰写不额外要求全项目盘点、覆盖率统计、发现项台账或浏览器验收；用户和项目已有的交付要求仍须遵守。明确要求深度审查时，再采用相应流程。

## 3. 展开字段、操作与场景规则

对本次受影响的路径，按适用性核对以下内容。页面有文档、字段有名称或类型，不代表规则完整；未知业务口径不得补猜。

| 内容     | 写清什么                                                                            |
| ------ | ------------------------------------------------------------------------------- |
| 字段     | 展示、输入、选择、计算、统计、筛选、状态和业务提示；名称/含义、来源、账号/权限范围、类型/格式/单位、默认/空值、必填、枚举（完整字典见下节）、精度/上下限、联动及可编辑条件 |
| 统计与计算  | 公式、对象、范围、时间、去重、重置、零值/缺失/失败表现及对关联数据的影响                                           |
| 操作     | 角色、可见/可用条件、确认、成功结果、取消/失败后的状态、刷新及再次操作                                            |
| 数据生命周期 | 产生者、更新者、持久化责任、读写时点、快照或实时取值；来源变化、旧数据和后续详情的表现                                     |
| 接口责任   | 管理页面维护的对象与服务端读写职责；请求、持久化、响应/详情映射、错误反馈和重试；缺少证据的端点、DTO（接口传输字段）及权限列技术待核验           |

承载规则的隐藏字段和请求参数也要追踪，普通装饰元素无需逐项列出。

### 枚举、状态与文案字典

写枚举、状态或页面可见文案时，**写完整字典，不只写改动项**。字典指本次触及的某一组业务值（一组枚举、一个状态机、一类页面文案），不是全系统所有值。

每个值至少写清：值本身（代码值与展示值）、业务含义、产生或出现的条件、展示文案、适用场景与权限范围。状态值还须写允许的转换、触发条件和转换结果；文案含动态内容时写模板及各变量的含义和取值来源。

字典只在一个权威位置成文——PRD、主页面规则明细或接口契约之一，按职责就近选择；其他位置引用该正文，不复制平行字典。原正文缺字典时本次整体补齐，可标明整理时点；缺失值核实后补，核实不了的列待确认，不猜填，也不以“历史欠账”只留半套；待确认项未补齐前，不将该字典标为完整。

已下线或仅为兼容保留的值可以保留，但须标明状态和适用边界，不得与现行可用值混列。

接收变更清单（CR）带来的字典改动时，逐值落回上述权威正文，不把字典变更只留在 CR 清单或代码注释里。正文更新与代码的同步时机由 CR 约定，PRD 侧负责让正文具备可承接的完整结构。

已有实现时，验收采用双向核对：先逐一追踪本次改动中的枚举、状态、文案变化到正文字典条目，再逐值核对正文与实现的条件、文案和场景。现行值无遗漏、无多余；已下线或仅为兼容保留的值按其标注单独核对，并记录位置与依据。

尚无实现时，依据已确认需求、设计和契约检查规则完整性，标明实现对照未执行，不因此要求先开发代码。记录依据；字典核对不代替行为测试或真实接口验证。

### 选择会改变结果的场景

先考虑正常、空/缺失、非法/边界值和失败，再按业务风险选择单条/多条、相同/不同对象、改选/清空、旧数据、失权、来源变更、超时、重复、并发或部分成功。不穷举无意义组合，不为检查场景自行增加功能；缺少实际规模或痛点依据的易用性建议列观察项。

跟踪同一业务对象在实际流程中的变化：未保存输入、已保存值、历史快照、外部条件变化后的复核、失败恢复及再次操作。可用“进入 → 修改 → 保存 → 提交 → 失败或退回 → 再次操作”帮助思考，按实际流程取舍，不固定步骤。

涉及多对象或多分组时，分别写各对象的结果、关联关系和恢复范围。区分打开页面、请求受理和业务完成；核对技术重试与新的业务尝试是否重复产生副作用，总体状态不能掩盖部分成功。

逐场景核对现行正文，判断完整、部分、缺失或冲突，再把已确认补充整合到对应章节。规则须能转成验收条件：身份和前置数据、操作、预期页面或数据结果。复杂边界补例子，已有测试可引用，不重复写能由规则直接推出的例子。

### 跨端对照（实际存在时）

比较业务含义相同的字段和动作，核对规则来源、各端读写时点、权限、状态、接口映射和失败恢复。合理适配差异写理由，未裁定差异交责任方；不按相似名称强行统一，也不默认某端是规则母版。共性规则集中定义，端差异放对应页面规则；无此关系时跳过。

## 4. 处理未决事项与证据

规则完整性、实现一致性和验证结果分别判断：业务已定但缺实现，登记实现待办；业务选择不明，交业务方决定；接口契约缺失，交技术方核验；缺运行证据，标未验证，不能据此判为实现缺陷。

问题优先登记到现有待办或 CR，写位置、条件、预期/实际、依据、责任、补齐条件及阻断范围，不要求每次新建台账。未决事项只暂停依赖它的内容。正文补齐可关闭文档问题；实现缺陷须有修复和复验依据才能关闭。

文档、源码、逻辑测试、构建、可见浏览器、自动化、CI 和真实接口证据分别说明能证明的范围。跳过或未执行不算通过，一端证据不代替其他端；文档更新不代表功能实现或生产验收。

## 5. 编辑、自审与交付

写前确定原段、插入位置及章节顺序。主规则先用一两句话讲清，边界按需要用字段表、例外表或示例展开。共性规则引用，删除重复解释；不为压缩篇幅合并不同判断或删去影响结果的条件。

用中文说明用户行为和业务规则，必要技术标识首次出现时解释含义与作用。句子写清主体、条件、动作和结果；上下文已明确的主体不用重复，多条件或例外拆开。业务规则、当前实现、历史和规划分开表述。同一概念固定名称，不同概念不强行统一；改写不得改变责任、取值时点、条件或结果，也不能掩盖原文冲突。

写完按读者路径通读整篇，检查大纲、段落衔接、术语、重复/冲突、更新记录和链接。从开发与测试视角确认：能找到要实现的行为，能逐字段找到条件、预期结果和边界。

另需核对：本次涉及的枚举、状态与页面文案是否已按 §3「枚举、状态与文案字典」整体成文，且只存在于一个权威正文；承接 CR 的字典改动是否已逐值落回正文，而非仍留在清单或代码注释里。

交付说明正文落点及理由、修改范围、依据状态、未决项及阻断范围、通读和链接检查结果；验证只报告本次实际取得的证据。
