# 写 PRD、页面规则与产品需求说明书

## 产出什么

四种文档，读者和用途不同：

- **规则正文**（PRD / 页面规则明细）：开发、测试照着做和验收的依据，规则以它为准。
- **产品需求说明书**（也叫阅读层）：给产品、开发、测试快速看懂页面要什么、边界在哪；只复述正文，不新增规则。
- **模块总览与索引**：只做导航，不定义规则，≤100 行。
- **字段/接口契约**：数据模型和服务职责的权威。

前两种是常见组合。也可以只写规则正文不写阅读层，但**不能只有阅读层没有正文**——阅读层是从正文改写出来的。项目没有页面内的阅读入口时，阅读层照样要写。

## 五条贯穿原则

1. **一条规则只写一处**。其他地方引用它，不复制；阅读层不能新增、改动或推断规则。
2. **不知道的不要编**。已确认的、代码里看到的、等技术核实的、历史的、以后要做的，分开写；拿不准交责任人定。
3. **没定的事要写出来**。阅读层必须有「待确认事项」。「按系统现有规则」只能用于明确由既有能力承接的部分（如数据权限、导出上限），真没定的必须进待确认表。
4. **按读者写**。不要把规则正文删减后当阅读层，也不要拿阅读层当验收依据。
5. **证据分等级**。文档、代码、单测、构建、浏览器、自动化、CI、真实接口各自能证明什么要说清；没跑的不算通过。

## 同一条规则被多处使用

两条判断标准，满足任一即属此类：同一条规则被**侧重点不同的**页面、入口或端使用（配置页与交易页、正文与审计页、不同仓库/端）；或同一个字段被多个动作使用（展示、选择、提交、审批、审计、导出）。同一个列表和详情只是展示同一字段，不算。

做法：

- 选一处完整写，这就是唯一权威；其他处写摘要并指向它。
- 写全条件到结果的判定：例外、时点、终态、失败或缺失时的表现不能省。
- 列一张「谁在用」的表：每个页面/端读什么、什么时候读、要写到多细、有什么差异、哪些还没接。
- 侧重不同：配置页写完整规则；发起页写来源、影响和例外；详情/审计页写什么时候展示、只读边界；另一端写怎么用、差在哪、还差什么。
- 规则散落多处时可以做一次同类排查，但先圈定范围、逐项记录、不改规则值。

不要：每个页面各写一份完整规则；下游只写「按系统规则」或「见相关文档」却不说来源、时点和影响（和原则 3 允许的引用既有能力不是一回事）；为了短删掉条件，或为了全复制全文。

小改按页面规则写就够了；只有横向、跨端、跨仓，或用户反馈「好几处说不清」时，才做全量排查，别把普通写作变成全量审查。

权威写在哪一处，看哪一处能完整表达这条规则（通常就是配置页）；由文档负责人定，拿不准交需求方。

## 写规则正文

先读 `page-rule-spec.md`。核对：

- **功能路径**：入口 → 同级入口/按钮/标签 → 下级页面/弹窗/提示 → 操作 → 结果；关联流程和共性规则。
- **字段与计算**：来源、账号/权限、格式/单位、精度、默认/空值、必填、枚举、上下限、联动、可编辑条件；公式、对象、范围、时间、去重、重置、零值/缺失/失败。
- **操作与数据**：可见/可用条件、确认、成功、取消/失败、刷新、再次操作；数据谁产生、谁更新、存在哪、读写时点、快照还是实时、后续怎么变。
- **字典**：本次涉及的枚举、状态、页面文案、业务失败的校验原因整组写全，只写一处。
- **场景**：正常、空/缺失、非法/边界、失败；按业务风险再看旧数据、失权、来源变更、超时、重复、并发、部分成功。
- **影响面**：同级入口、子页面、弹窗、旧链接、兼容入口、接口消费者、测试。
- **未定与证据**：位置、条件、预期/实际、依据、责任人、什么条件解除、影响哪些任务。
- **写清楚**：结论先行；同一概念用一个名字；业务、实现、历史、规划分开写；更新记录和链接要检查。

这七项是逐项核对的清单。本次确实不涉及的（例如纯静态页没有计算）要写「不适用」并说明，不能空着不说。

## 写产品需求说明书

先读 `product-requirements-spec.md`。要求：

- **前提**：正文已经有了。没有就先补正文，或者先在文档里标出这块缺口，不要凭空写。
- **结构**：概述 → 用户与权限 → 结构流程 → 规则/字段 → 状态与操作 → 异常与空态 → 验收 → 范围边界 → 待确认事项 → 口径说明（本文没展开的按现有规则执行）；模块级另用一套（定位 → 页面与文档索引 → 阅读顺序 → 范围边界 → 待确认事项 → 口径说明）。这里的「验收」章写的是读者怎么判断页面做对了，不是 CR 的验收清单，也不能替代它。
- **文档头**：适用范围、依据版本、文档负责人、谁维护规则、变更找谁。
- **待确认事项**：表格列「编号/问题/影响/谁定（业务/产品/技术）/当前状态/读者该做什么」；正文未定处标【待确认】；没有就写「暂无」。未定的事只有一份清单：正文里标位置、阅读层给人看、CR 里挂任务和停止条件，状态以正文为准。
- **原因要列全**：正文里已有、边界明确、能列全的原因（导入失败、审批驳回、权限拒绝等），阅读层要写全；可以按同一个修正动作合并，但不能丢条件、不能用「等」兜底；下载或日志入口不能替代原因说明。
- **怎么写**：一件事一条，条目开头加加粗标签；穷举类（失败类别、字段、条件组合）做成表格；不写多段连续叙述；新增或改动的章节照既有章节的写法，全文呈现方式统一。
- **多处共用的规则**：可以放摘要或判定表，但要指向正文。
- **不要写**：实现细节、接口、Mock、代码路径、行号、CR/测试编号、更新记录、像素阈值、英文 UI 术语、元写作说明行（「本文不写…」这类自指句）。变更历史也不写，要追溯去看正文、CR、git。更新记录只留在规则正文里，阅读层不写、查看器也不显示，这是三层各自的分工。
- **篇幅**：不超过正文 50%（目标 15~30%）；模块总览 ≤100 行；范围说明页 ≤40 行。

## 正文和阅读层怎么对齐

读 `projection-and-governance.md`。要点：

- 规则以正文为准，阅读层是改写给读者看的版本。
- 规则值、权限、状态、枚举、文案、数据来源/读写边界变了 → 两边一起改；只是表达精简 → 只改阅读层。
- 说法冲突时：最新 CR 的裁定 > 正文 > 阅读层；判断不了交责任人。
- 交付前抽 3~5 个关键点（枚举、状态、权限、边界）对一遍，记下位置。涉及多处共用的规则，还要看「谁在用」的表是否覆盖全部实际页面/端、各处的指向是否还有效。
- 文档负责人对两边同步负责，变更找谁写在文档头。

## 怎么做

**单篇**：定类型 → 读依据和索引 → 列缺口（已确认/仓内已有/待确认/体例）→ 判断是否多处共用 → 写 → 自检（长文档加做读者测试）→ 交付说明。

**批量**：先定一篇样板 → 用户确认体例 → 分模块分批 → 并行写 → 合并检查 → 抽读 → 清缺口；见 `batch-refactor-playbook.md`。涉及多处共用的规则或同类问题反馈，另按 `cross-cutting-rules.md` 做一次有范围的排查。

任何情况：没确认的不要猜；没定的进待确认表；技术待核实不等于业务没定。

## 交付时说明

写了什么类型、放在哪、为什么；改了哪些范围；依据状态（已确认/技术待核验/历史）；还有哪些未定、卡住什么；通读和链接检查结果；实际拿到什么证据（文档检查/抽读/读者测试，没做的单列）。

## 不管什么

- 页面内文档入口、查看器、构建复制、搜索、生产暴露 → `requirements-docs-viewer`
- 变更清单/CR 的范围、任务、验收、合并 → `change-list-authoring`
- 项目索引、交付包、日报、AGENTS 状态 → 项目自己的流程
