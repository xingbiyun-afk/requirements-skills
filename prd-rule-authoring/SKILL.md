# 产品需求文档（PRD）、页面规则与产品需求说明书写作

## 目标

把需求写成**不同读者能定位、理解和验证的现行文档**：

- **规则正文**（PRD/页面规则明细）：供开发、测试执行与验收的**权威规则**；
- **产品需求说明书**（阅读层）：供产品、开发、测试接手**阅读**的精简说明。

两类文档可同时存在，也可单独存在。阅读层是独立交付物：项目没有页面内阅读入口时也要产出。

## 阅读顺序

| 文件 | 何时读 |
|---|---|
| `references/document-types.md` | 每次先读：选文种、读者、粒度与长度 |
| `references/cross-cutting-rules.md` | 规则影响多个消费侧重不同的页面/入口/端，或出现规则散落、过度简化时 |
| `references/page-rule-spec.md` | 写规则正文（PRD/页面规则明细）时 |
| `references/product-requirements-spec.md` | 写产品需求说明书（阅读层）时 |
| `references/projection-and-governance.md` | 从规则正文投影阅读层、维护双轨时 |
| `references/quality-checklist.md` | 完稿自审与交付前 |
| `references/batch-refactor-playbook.md` | 一次改造多篇文档时 |

> `archive/` 内为历史原文（如 v1 SKILL），**不加载**，仅供回溯；不要从中取用规则。

## 0. 边界（先确认不越界）

- 本技能**只产出文档**：不规定页面内阅读入口、查看器、构建复制、搜索的实现；该能力属于独立技能 `requirements-docs-viewer`。
- 阅读层不因“项目暂时没有阅读入口”而省略；入口只是它的一个消费方。
- 变更清单/CR 的范围、任务与验收由 `change-list-authoring` 负责；本技能只负责正文。
- 不把开发文档直接改标题当阅读层；两类文档的读者与完整性口径不同。

## 1. 先选文种与读者

- **规则正文**（整体 PRD / 页面规则明细）：规则值权威，供开发、测试、验收执行。
- **产品需求说明书**（阅读层）：重述权威、不新增规则值，供快速理解页面/模块边界。
- **模块总览与索引**：只导航，不定义规则。
- **字段/接口契约**：契约权威。

读者、权威性、未定事项、历史、长度与落点的完整对照及选择顺序，见 `references/document-types.md`；本节不重复列出，避免两处漂移。

一个规则值只在**一处权威正文**成文；阅读层只重述；模块总览只导航；契约按接口职责就近落点。

## 2. 共同原则

1. **权威唯一**：同一规则值只有一处权威正文。阅读层不得新增、修改或推断规则值。
2. **未知不猜**：已确认规则、代码事实、技术待核验、历史记录、未来规划分开表述；无法判断的交责任方裁定。
3. **未定如实**：真正的业务未定项必须在阅读层以「待确认事项」呈现（见 §4），**不能用「按系统现有规则」掩盖**。
4. **读者优先**：每个文种按自己的读者写；不要把规则正文压缩后直接当阅读层，也不要把阅读层当验收依据。
5. **证据分级**：文档、源码、逻辑测试、构建、可见浏览器、自动化、CI、真实接口证据分别说明能证明的范围；跳过或未执行不算通过。
6. **横向规则先定权威**：同一规则影响多个消费侧重不同的页面/入口/端时，先确定唯一权威落点，再规划各消费方写什么；下游文档摘要 + 回链，不写平行全文。
7. **按影响面取深度**：单页小改按页面规则写；横向、跨端、跨仓或用户反馈“多处说不清”时，才启用规则包、消费方矩阵和全量排查，避免把普通撰写变成全量审查。

## 2.1 横向规则（多页面 / 多端共用）

先判断是否属于横向规则：同一规则影响多个消费侧重不同的页面/入口/端（含配置与发起、详情与审计、不同仓/端等；同一列表与详情只是展示同一字段不算），或同一字段被多个消费动作（展示、选择、提交、审批、审计、导出）使用。满足则按 `references/cross-cutting-rules.md` 建立**规则包**：

- 唯一权威落点：规则值只在一处完整成文；其他文档写摘要 + 回链；
- 完整字典与判定顺序：条件 → 结果，例外、时点、终态、失败/缺失表现不可省略；
- 消费方矩阵：谁消费、消费什么、何时读、需要写到多细、双端/多仓差异与待承接；
- 侧重不同：管理/配置页写完整规则；发起/交易页写来源、使用影响和例外；详情/审计页写展示时点与只读边界；另一端写消费方式/差异/待承接；
- 可读性：多条件拆编号/表格，不压成一句；同一概念固定名称，近义名称解释差异；
- 同类问题有边界地全量排查：定分母、逐项记录、规则值零变更、未改项有理由；小需求不强制。

不要：
- 在每个页面各写一份“完整规则”；
- 下游只写“按系统规则”或“见相关文档”，不写来源、时点和影响；
- 为简短删掉影响结果的条件，或为完整复制全文。

## 3. 规则正文模式（开发/测试权威）

先读 `references/page-rule-spec.md`。最小核对清单：

- **功能路径**：入口 → 同级入口/按钮/标签 → 下级页面/弹窗/提示 → 操作 → 结果；关联流程与共性规则；
- **字段、统计与计算**：来源、账号/权限、格式/单位、默认/空值、必填、枚举、精度/上下限、联动、可编辑条件；公式、对象、范围、时间、去重、重置、零值/缺失/失败；
- **操作与数据生命周期**：可见/可用条件、确认、成功、取消/失败、刷新、再次操作；产生者/更新者/持久化/读写时点/快照或实时；
- **枚举、状态与文案字典**：本次触及的整组字典完整成文，只在一处权威；
- **场景**：正常、空/缺失、非法/边界、失败；按业务风险选择旧数据、失权、来源变更、超时、重复、并发、部分成功；
- **未决与证据**：位置、条件、预期/实际、依据、责任、解除条件、阻断范围；
- **影响面**：同级入口、子页面、弹窗、旧链接、兼容入口、接口消费者、测试；横向规则另见 §2.1 消费方矩阵；
- **编辑要求**：结论先行、同一概念固定名称、业务/实现/历史/规划分开、更新记录与链接检查。

## 4. 阅读层模式（产品需求说明书）

先读 `references/product-requirements-spec.md`。最小要求：

- **前置**：权威正文已存在。缺权威时先补权威或在文档中标注缺口，不直接编造。
- **骨架**（按页面裁剪）：概述 → 用户与权限 → 结构与流程 → 规则/字段/列表 → 状态与操作 → 异常与空态 → 验收 → 范围边界 → **待确认事项** → 口径说明；模块级用：模块定位 → 页面与文档索引 → 阅读顺序 → 范围边界 → 待确认事项 → 口径说明。
- **元信息**（文档头）：适用范围、依据版本/日期、**文档负责人**、口径维护人、变更处理入口。
- **待确认事项（必须保留）**：表格列「编号 / 问题 / 影响 / 需谁裁定（业务/产品/技术）/ 当前状态 / 读者动作」；正文中未定内容标【待确认】。不得省略、不得写成已定；没有未定项时写「暂无」。
- **横向规则**：阅读层可保留摘要或判定表帮助阅读，但必须回链权威正文；不复制完整规则，不新增/修改规则值。
- **「按系统现有规则」的使用边界**：仅用于已明确由既有能力承接的口径（如数据权限、导出上限）；真正未定的内容必须进待确认表，不得用这句话含混过去。
- **文体**：结论先行、一句话能说清不展开；中文用户语言；禁实现/接口/Mock/代码路径/行号/CR 或测试编号/历史快照/更新记录/英文 UI 术语/像素阈值/元写作说明行。
- **历史**：不写变更历史；可追溯性由权威正文 + CR + git 承担；变更只更新现状与待确认表状态，不写变更叙事。
- **长度**：≤权威正文 50%，目标 15~30%；模块总览 ≤100 行；范围说明页 ≤40 行。

## 5. 双轨治理

读 `references/projection-and-governance.md`。要点：

- **权威分工**：规则值以规则正文/PRD/契约为准；阅读层是读者投影。
- **同步触发**：规则值或权限/状态/枚举变化 → 两轨同单更新；仅表达精简 → 只改阅读层。
- **冲突裁定**：最新 CR 裁定 > 规则正文 > 阅读层；无法判断交责任方。
- **漂移检查**：交付前对照关键枚举、状态、权限、边界（3~5 个抽点），记录位置；横向规则另核对消费方矩阵是否覆盖全部实际消费方、下游回链是否有效。
- **责任**：文档负责人对双轨同步负责，变更处理入口在文档头写明。

## 6. 工作流程

**单篇**：定文种 → 读依据与索引 → 列缺口（已确认/仓内留底/待确认/体例）→ 判断是否横向规则（§2.1）→ 写作 → 自审（quality-checklist；长文档或多章节加做读者测试 §2.2）→ 交付说明。

**批量重构**：样板定稿 → 用户确认体例 → 按模块分批 → 并行写作 → 集成与机械检查 → 可读性抽读 → 缺口清单闭环；见 `batch-refactor-playbook.md`。横向规则或同类问题反馈另按 `cross-cutting-rules.md` §7 做有分母的全量排查。

任何情况下：未确认不猜填；未定进待确认表；不把技术待核验写成业务未定。

## 7. 交付说明

交付时说明：文种与落点及理由、修改范围、依据状态（已确认/待核验/历史）、未决项与阻断范围、通读与链接检查结果、实际取得的验证证据（文档检查/抽读/读者测试/未执行项分别列）。

## 8. 不覆盖

- 页面内文档阅读入口、查看器、构建复制、搜索、生产暴露面 → `requirements-docs-viewer`；
- 变更清单/CR 的范围、任务、验收与合并流程 → `change-list-authoring`；
- 项目索引、交付包、日报、AGENTS 状态 → 项目自身流程。
