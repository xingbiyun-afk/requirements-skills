# 规则与文档影响传播

用于识别“这次改动不只改一个页面/一个字段，而是改变了一条被多页面、多端或多文档消费的规则或文档结构”的变更清单。目标：把规则权威、下游文档、双端/多仓和同类排查写成可执行任务，避免代码改了、文档散着改或只改一句。

> 本文件侧重 CR 的任务拆分、影响矩阵和验收；规则如何判断横向、如何写唯一权威/消费方矩阵/判定顺序/可读性，以 `prd-rule-authoring` 的 `cross-cutting-rules.md` 为写作规范，本文不重复定义。

## 1. 何时启用

满足任一条件：

- 改变某条规则的业务含义、判定条件、例外、状态/时点或口径；
- 改变共享字段/状态的语义、枚举、展示或读写时点；
- 改变阅读层/规则明细的权威结构（新增/迁移权威段、合并分散规则、建立回链）；
- 同一规则影响多个消费侧重不同的页面、入口、端或仓（同一列表与详情只是展示同一字段不算）；
- 用户/评审反馈“规则散落、过度简化、多处不一致”。

单页单字段的小改不需要套用；在 CR 中写明“不涉及横向规则/文档结构变更”即可。

## 2. 影响矩阵（CR 必填）

| 编号 | 规则/字段/结构 | 现行权威位置 | 受影响文档/消费方 | 本单动作 | 同步时机 | 验收 |
|---|---|---|---|---|---|---|
| I-01 | （规则名/字段/章节） | （PRD/规则明细/契约路径+章节） | （配置页、交易页、详情页、另一端/仓、阅读层、内部底稿） | 完整改写 / 摘要+回链 / 只登记 / 待承接 | 同 PR / 后续 | （检查点与证据） |

要求：

- 一行只承载一个可独立验收的规则/结构变更；
- 权威位置必须具体到文档和章节，不写“相关文档”；
- “本单动作”必须可执行：完整改写、下游摘要/回链、内部底稿同步、双端消费差异、待承接登记；
- 受影响消费方按实际存在列出，不虚构；
- 同一规则不能出现在两处“完整改写”，否则必须明确唯一权威并让另一处降级为摘要/回链。

### 2.1 技术事实面（第二根轴）

矩阵的“受影响文档/消费方”按页面与端清点，容易漏掉不进规则正文、但会被读者当成真的**技术事实面**——改了规则、正文也同步了，对照表/注释/fixture 仍停在旧口径。按变化类型补充清点，命中即单独成行：

| 变化类型 | 必须清点的技术事实面 |
|---|---|
| 字段、枚举、类型、取值域 | 技术字段/Mock 对照表、类型定义、静态样本（fixture）、测试台账 |
| 数据来源、读写边界、存储形态、会话生命周期 | Mock 构造与头注、模块 README、代码中的口径注释、测试夹具 |
| 状态机、权限、菜单、空态 | 入口与基线文档（AGENTS 等）、模块 README、索引 |
| 页面行为、交互时序 | 回归用例清单、e2e 场景名、测试台账计数 |

**判断无需改动时须给证据**：写扫描范围（目录/文件集）与命令（例：`grep -rn "<旧口径>" <路径>`），只写理由不算完成；这类行记为“仅登记 + 证据”，不得省略。历史计数、旧样本规模只允许出现在更新记录/历史表，不得裸写在现行段。

## 3. 任务类型

### 3.1 权威收敛

- 确定唯一权威落点；
- 把分散的完整描述合并到权威段；
- 下游页面改为摘要 + 回链；
- 检查原有重复段落/旧链接/索引；
- 验收：权威唯一、下游无平行全文、回链有效。

### 3.2 下游消费同步

对每个消费方写清：

- 该方为什么要看这条规则；
- 读取/写入时点；
- 对展示、选择、提交、审批、审计、导出的影响；
- 例外与失败/缺失表现；
- 哪些内容不在此处重复、回链到哪里。

常见侧重：配置/管理页完整；发起/交易页来源+使用+影响+例外；详情/审计页展示时点+只读/快照边界；另一端消费方式+差异+待承接。具体按 `prd-rule-authoring` 的横向规则规格执行。

### 3.3 双端/多仓同步

- 先确认规则权威和消费方；
- 分别列代码/文档改动、依赖、同步时机、验收证据；
- 未实现端写“待承接/只读参考”，不假装已完成；
- 不以一端代码/测试/PR 代替另一端验收。

### 3.4 同类问题全量排查

当用户反馈“同类问题多处”或本次改的是横向规则时，增加全量排查任务：

- **分母**：哪些文档/章节/消费方，明确范围；
- **问题类型**：多条件压句、规则分散/重复、缺例外/时点、术语不统一、权威缺失；
- **权威源**：用户裁定 > 权威正文/契约/代码事实 > 阅读层表达；
- **记录**：文档、章节、问题类型、原文摘要、修订、权威源、双轨同步、未改原因；
- **验收**：分母覆盖 100%、未改项有理由、规则值零变更（除确认口径）、链接/结构检查通过。

小需求不强制全量；只有横向规则、同类反馈或明确要求时启用。

## 4. 文档质量验收

文档类任务不能只验收“文件已改”，至少检查：

- 权威唯一，页面是摘要+回链，不是平行全文；
- 多条件/例外拆编号或表格，没有为“精简”删条件；
- 同一概念固定名称，近义名称解释差异；
- 双端/多仓的权威、差异、待承接和证据边界清楚；
- 阅读层不新增/修改规则值；规则值变化只在权威正文；
- 链接 0 断链，标题/结构/表格无异常；
- 全量排查有分母、逐项记录和未改理由。

## 5. 证据与状态

- 文档检查、逻辑测试、构建、可见浏览器、自动化、CI、真实接口分别记录；
- 文档改完不等于功能实现，实现完成不等于生产验收；
- CR 中分开写：规则完整性、实现一致性、验证结果、任务完成；
- 未执行项列明，不用“基本完成/整体正常”掩盖。

## 6. 反模式

- CR 只列代码/页面任务，不列规则权威和文档同步；
- 同一规则在多个页面各写一份完整版；
- 下游只写“按系统规则/见相关文档”，没有来源、时点和影响；
- 双端只写“同步”不写差异、待承接和证据边界；
- 把“改文档”当成一句任务，没有落点、分母和验收；
- 发现同类问题只改示例句，不做有边界的全量排查；
- 用“文档已更新”代替结构/可读性检查。

## 7. 交付自检

- [ ] 影响矩阵覆盖实际消费方，权威位置具体。
- [ ] 每个消费方有动作和验收，未实现/未承接有明确状态。
- [ ] 权威唯一，下游无平行全文，回链可到达。
- [ ] 文档质量与双端/多仓证据分别验收。
- [ ] 如做全量排查：分母、记录、未改理由、规则值零变更、链接/结构检查齐全。
- [ ] 不把普通小改升级为全量审查。
