# 从审查到可执行变更清单的通用方法

## 使用范围

用于深度审查、查遗漏和盲区、核对字段级覆盖，或把审查发现转成 CR。按用户目标选择局部影响审查、模块审查或全量审查；记录参与仓库/端、运行版本、纳入范围、排除理由、前置任务和可用证据。全量盘点不是所有 CR 的默认要求。

方法主线：入口盘点 → 字段与操作矩阵 → 状态及操作链场景 → 规则/实现/证据对账 → 发现项和验收。允许根据发现补充前面的清单；不要先宣布功能整体满足，再跳过字段和异常边界。

## 1. 用实际入口确定审查范围

从当前路由、菜单、页面跳转、权限守卫、运行组件和测试入口交叉确认在用页面；包含标签页、弹窗、抽屉、子页面、条件区块及无独立路由的操作入口。区分运行实现、参考实现、未接入功能和历史归档，不凭目录名或文档标题判断是否在用。非页面项目用 API、命令、后台任务或其他真实入口替代页面。

| 入口/组成部分 ID | 仓库/端与版本 | 入口、角色及可达条件 | 代码/路由/组件 | 对应规则/测试 | 纳入状态与理由 |
|---|---|---|---|---|---|

清单与实际注册及调用关系双向核对：既找“清单漏了哪些入口”，也找“清单列出的入口是否仍在用”。隐藏或权限限定不等于不存在；不能确认时列待核实及下一步。共用组件可复用检查结果，但要核对各调用处的参数、权限和业务差异。

## 2. 逐字段、逐操作建立矩阵

枚举纳入页面的展示、输入、选择、计算、统计、筛选、表格列、状态和业务提示，以及按钮、导入/导出和批量动作。核对文档要求但页面缺失的项，以及页面/代码存在但规则未说明的项。承载规则的隐藏字段、请求参数和关联标识也应追踪；普通装饰元素不必当业务字段列满矩阵。

字段 ID 与页面 ID 关联。字段清单和规则正文分开维护时，引用已有规则，不另造一套权威正文。按适用性填写下列维度；“不适用”写理由，“未知”写缺证据和责任方。

| 维度 | 核对内容 |
|---|---|
| 名称与含义 | 用户可见名、业务定义、代码/契约字段映射、单位；同义词是否统一，近似术语是否含义不同 |
| 来源与责任 | 产生者、读取来源、更新者、前后端及外部系统责任；请求、存储和消费者的映射 |
| 取值与约束 | 类型/格式、字典/枚举、默认/空值、必填、上下限、精度、联动和非法值处理 |
| 权限与操作 | 哪些角色可见、可选、可编辑、可操作；条件变化和失权后的结果 |
| 取值时间 | 进入/刷新/保存/提交/后续处理时何时读写；快照或实时，来源变化后如何复核 |
| 计算与影响 | 公式、统计对象/范围/时间/去重/重置、零值；对关联对象、汇总和后续流程的影响 |
| 状态与异常 | 加载、空、失效、失败的展示/校验；保存、刷新、返回和恢复后的值 |
| 来源与证据 | 现行规则位置、代码符号、测试编号、运行证据及日期；未检查项和适用边界 |

操作矩阵至少写“谁、什么条件、执行什么动作、成功结果、取消/失败后的状态、能否及如何再次操作”。可见与可用分别核对；打开页面、点击按钮、请求受理、业务处理完成不能混为同一步。

## 2.1 横向规则与多消费方

同一规则被多个消费侧重不同的页面/入口/端消费时，逐消费方核对：来源、读取/写入时点、对选择/提交/展示/审核的影响、例外与失败表现、哪些内容是摘要/回链。确认唯一权威落点，避免多个页面各写一份完整规则。双端/多仓分别核对差异与待承接，不以一端完成代表另一端。小需求不强制全量；只在横向规则、同类反馈或明确要求时建立分母并做同类排查。

## 3. 用结果差异选择异常与操作链场景

按业务风险挑选会改变结果的场景，不机械穷举所有字段值组合。适用候选包括：正常、空/缺失、边界/非法、单条/多条、相同/不同对象、选择/改选/清空、取消/返回、重复操作、旧数据、失权、来源变更、超时、并发、服务失败、部分成功及恢复。不适用的风险类别注明理由；不为场景检查自行增加产品功能。

| 场景 ID | 入口/字段/操作 | 角色、初始状态及数据 | 操作或条件变化 | 预期值/状态/副作用 | 取消、失败、再次操作 | 规则/代码/验证证据 |
|---|---|---|---|---|---|---|

除单次操作外，跟踪同一对象经过实际存在的多个步骤，检查未保存输入、已保存值、历史快照、关联对象及外部条件变化。可用“进入 → 修改 → 保存 → 提交 → 失败或退回 → 再次操作”帮助思考，但按项目真实流程删改节点。区分技术重试与新的业务尝试，核对重复请求和恢复是否重复产生副作用。

多对象/多分组流程分别记录结果、占用/释放、金额/数量、关联关系和恢复对象；整体状态不能掩盖某个对象已经成功或仍待处理。并发和异步场景区分前端禁用、后端受理、原子校验、幂等和结果查询，缺契约时不靠 Mock 推断。

容量/易用性建议先区分“当前功能违反已确认规则”与“缺少真实规模或痛点依据的优化”。合成大数据可验证性能边界，不能证明真实用户需求；没有使用证据时列观察项，不臆造数量上限、搜索或排序需求。

## 4. 规则、实现、验证与交付状态分别对账

确认审查时点的正式决定、PRD、页面规则、字段/接口契约和当前代码；历史 CR、日报及总结用于追溯。明确项目的权威来源，冲突逐项列来源、说法、时点和影响，交责任方裁定。代码行为不是未定业务规则的答案；后来的修复不能补证历史快照当时已覆盖。

不要用一个“已完成/待确认”状态代替以下独立判断；一项发现可同时有多个问题类别。

| 维度 | 适用判断 | 需要的依据 |
|---|---|---|
| 规则覆盖 | 完整 / 部分 / 无说明 / 冲突 / 不适用 | 是否写清适用条件、字段、结果和异常；文档存在或字段有名称不算完整 |
| 实现对照 | 符合 / 部分实现 / 缺失 / 不一致 / 未检查 | 对应代码、调用关系及版本；静态代码符合不等于运行验收通过 |
| 验证结果 | 通过 / 失败 / 跳过 / 未执行 / 待核实 | 方法、环境、数据条件、预期/实际、日期和可复核证据 |
| 任务状态 | 未开始 / 进行中 / 已完成 / 后置观察 / 范围外 | 是否达到约定完成定义，尚缺责任/前置条件；不把技术待办误标业务待决定 |

已确认业务规则缺实现，登记为实现任务；材料无法确定业务选择，列选项、影响和待业务决定；业务已定但真实接口、DTO、权限或恢复契约缺证据，交技术负责人核验。已实现仍挂“待确认”、功能取消却仍列本期、历史“未提交”被写成当前状态等问题，回填日期、现行结论和后续链接，保留必要历史。

### 多端/多仓对照（实际存在时）

按[跨端与跨仓协作](dual-repo-and-review.md)记录实际参与方、同义行为差异和各方证据；无此关系时跳过。

## 5. 分清证据能证明到哪里

不同证据证明不同范围，不能互相替代。按项目实际工具记录；尊重用户指定浏览器或其他验证渠道，没有相应工具时说明缺口。

| 证据类型 | 可支持的结论 | 不能由此推断 |
|---|---|---|
| 文档/正式决定 | 业务要求、责任、范围和取值时间 | 功能已实现 |
| 源码/调用链 | 静态实现、依赖和数据流 | 运行成功、真实接口可用 |
| 逻辑/组件测试 | 被测试输入下的规则结果 | 页面全流程或生产集成 |
| 构建/静态检查 | 编译、格式、类型和链接等检查结果 | 业务行为正确 |
| 可见浏览器交互 | 指定环境下页面行为、提示及结果 | 未操作场景或真实服务已验收 |
| 浏览器自动化 | 对应环境和断言范围内的结果 | 自动代替指定可见浏览器验收 |
| PR/main CI | 对应提交和实际作业的检查结果 | 跳过项通过、生产已上线 |
| 真实接口/集成或生产证据 | 被验接口、角色、环境和流程结果 | 超出权限、数据或场景范围的结论 |

记录提交/版本、环境、命令或步骤、合成/脱敏数据、预期/实际、结果、时间和证据位置。跳过、未执行、启动失败未进入断言均不算通过。遵循项目数据访问边界，优先采用合成数据和非敏感契约，不擅自索取或读取敏感数据。

## 6. 将发现写成可执行任务并独立验收

发现项可先登记在现有 CR/台账，不强制每次新建全部产物。按标准模板 §7.5 登记唯一 ID、问题类别/优先级、位置与条件、规则来源、预期/实际、证据及缺口、责任方、依赖、精确落点、验收和关闭依据。仅因缺证据怀疑的问题标“待核实”，不能直接写成确定缺陷。

按风险与依赖排序：数据破坏、金额/权限/并发等结果风险；规则与实现不一致；缺失规则/技术契约；文档状态和术语；有依据的易用性优化或后续观察。项目有严重度标准时沿用，不以此示例自行固定等级。

验收分别回答三个问题：

1. **范围是否盘点完整**：入口清单与实际注册/调用关系无未解释的差异，页面和字段/操作分别有完整清单、排除理由和待核实项。
2. **结果是否已验证**：每个相关场景有预期、实际、方法和证据；缺少的验证范围、失败和未执行项可定位。不得把“已登记”算为“已验收通过”，或用一个总体百分比隐藏缺页。
3. **发现是否已修复关闭**：以修订后的实现/规则及针对性复验关闭具体发现 ID，并同步测试台账、更新记录和回链。仅完成审查报告时可报告“审查完成、修复待办”，不能称全部问题已解决。

覆盖率只在有可核对分母时报告，按页面、字段/操作和场景分别给分母来源及完成/待核/未执行数。全面审查仍应说明运行版本、工具与生产证据边界，不能承诺从此不存在遗漏。
