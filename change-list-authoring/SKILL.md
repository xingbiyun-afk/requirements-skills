# 写可执行的变更清单

## 目标

把需求写成接手者能照着做、也能验收的任务。写清单不等于授权开发、提交、推送或建 PR；用户已经给的执行授权继续有效。

按任务读参考文件：

| 什么时候 | 读哪个 |
|---|---|
| 写或审查清单 | `change-list-template.md` |
| 深查、找遗漏、核对字段覆盖、把审查发现转成任务 | `review-method.md` |
| 真有跨端承接、多仓同步或独立规则母版 | `dual-repo-and-review.md` |
| 改到多处共用的规则、共享字段/状态或文档结构 | `rule-and-doc-impact.md`（这条规则**怎么写**归 `prd-rule-authoring`；**这次改动影响哪些文档**归本技能） |
| 想参考历史文档的结构或验收粒度 | `project-patterns.md` |

## 怎么做

1. **定范围**：确认日期、编号、阶段、参与仓库、只读参考、交付类型，并写清这份清单的**完成定义**（做到什么算完、什么不算）——就在清单开头那一节，跟用户对齐。先读项目现有的协作规则、启动说明和文档入口。普通 CR 只看受影响的页面和必要入口；全面审查才盘全部在用页面。
2. **核现状**：看分支、工作区、合并记录、路由、组件、测试，找到现行的 PRD、页面规则和接口契约。业务规则、代码事实、待核实的契约、历史、规划分开记。被新决定替代的旧规则不再算现行；冲突说不清的，列出来源、说法、时点和影响交责任人。审查历史快照只用当时能拿到的证据，后来的修复不能追认为当时已覆盖。
3. **盘点影响**：逐项标明新增/修改/删除，并顺着同级入口、子页面、弹窗、字段、操作、状态找下去。删除的要查旧链接、兼容入口、接口消费者和测试；新增或修改的要核对共性规则和关联流程。改到多处共用的规则、共享字段/状态或文档结构时，按 `rule-and-doc-impact.md` 列影响表（写在哪、谁受影响、做什么、什么时候同步、怎么验收），并把要不要做同类全量排查显式写出来。需要深审时按 `review-method.md` 建矩阵和发现项。
4. **写成任务**：一个 ID 一个可交付结果，写清仓库、文件或文档章节、输入来源、条件、动作、结果、异常、验收。缺信息先补证据；仍判断不了就写问题、影响、责任人、解除条件、卡住哪些任务。会改实现方向的未定项只暂停依赖它的子项，已授权且不依赖它的工作照常做。
5. **整理文档**：沿用项目目录和命名，按模板保留核心章节，条件章节按需填。优先改现行正文，复用已有索引，不另起一套规则。逐文件写清改哪里、改什么、什么时候改、怎么指回；不改正文也要写理由和要更新的状态记录。
6. **交付前自审**：照下面的门槛过一遍，通读受影响文档的术语、衔接、冲突和链接。回报清单路径、结论、证据范围和未决项；草案、正式版、实现、验收状态分开说。

## 质量门槛

- **任务能落地**：每项写清改哪里、依赖什么、产出什么、怎么客观验收。写「按现有逻辑」要给文件和符号以及继承的行为，不能只写「优化一下」或「参考现有页面」。
- **字段有规则**：范围内的展示、输入、计算、统计、筛选、状态、业务提示都对应到规则正文或引用。核对来源、账号/权限、格式/单位/枚举/精度/上下限、默认/空值、必填/可编辑、读写时点、快照还是实时、后续怎么变；统计还要说清对象、范围、时间、去重、重置、零值/缺失/失败。不知道的不猜。
- **字典跟着改**：本次新增、修改或下线的枚举、状态、页面文案、业务失败或校验原因，都要**整组**写进现行正文，和代码同一个 CR、同一个 PR 合；顺带发现和小幅收口也算，不能事后补单。原来缺字典的整组补齐，特殊值和兼容值加业务注释。清单里写清正文路径、章节、同步时机和验收点（登记和双向验收见模板 §8）。
- **操作有结果**：可见、可用、确认、成功、取消、失败、刷新、再次操作逐项写。按适用性覆盖正常、空数据、会改变结果的边界；操作链检查中途变更、失败恢复、旧数据、失权、重复、并发，不穷举没意义的组合。
- **数据责任清楚**：管理页面、服务提供方、请求/存储/消费端分别说明。没契约就列为技术待核实，不能拿菜单或 Mock 推真实接口、字段、权限和能力。
- **证据可复核**：验收点写环境、版本、命令或步骤、预期结果、证据类型。文档、源码、单测、构建、浏览器、自动化、CI、真实接口、生产证据分开记；没跑的不算通过。沿用项目自己的测试分层，不强推某项目的 L0/L1/L3 叫法。
- **状态别混**：规则是否完整、实现是否一致、验证是否做过、任务是否完成，分开判断。业务已定但技术契约缺失不算业务待决定；审查做完不代表发现项已修。覆盖率要有可核对的分母，页面、字段/操作、场景分开报，列出未核实、未执行、排除项。
- **文档链闭合**：已确认的规则有来源；改过的**权威正文**有更新记录和能用的指回链接（阅读层不写更新记录，改到阅读层时记在正文里）；历史记录标时点。跨端/跨仓只在真参与时分别登记责任和证据，不能一端完成就算都完成。
- **横向规则有传播**：改到多处共用的规则、共享字段/状态或文档结构时，影响表必须覆盖权威写在哪、实际谁在用、双端/多仓差异、各处摘要与指向、以及要不要做全量排查；不能只写代码或页面任务。
- **文档质量可验收**：文档类任务要验收权威只有一处、各处是摘要加指向、判定和例外读得懂、术语一致、双端边界清楚、链接和结构没问题；不能只以「文档已改」关闭。
- **文字简明**：关键规则写清主体、条件、动作、结果；复杂条件拆开；同一概念用一个名字；共性规则引用一次不重复；删字不能改变责任、条件、取值时点或结果。技术标识首次出现时说明业务含义。

正式版可以带明确列出的未决项，但不能把它们写成已确认需求；依赖它的任务要有停止条件。只有达到前面写明的完成定义，才能把清单或发现项标为已关闭。
